# Feature Specification: 여러 사람이 쓰는 나비스 — 회원마다 기억 분리

**Feature Branch**: `main` (전용 기능 브랜치 미생성 — git 확장 훅이 등록되어 있지 않다)

**Created**: 2026-10-08

**Status**: Draft

**Input**: User description: "나비스 이제 여러사람 쓸 수 있도록 로그인 회원 마다 기억 나누기! 분리 회원마다
해당 기억 생기게" — 확정된 결정: 가입은 관리자가 계정을 만들거나 초대한다(가입 화면 없음) ·
Claude 토큰은 회원마다 자기 것 · 외부 MCP(Claude Code 연결)는 관리자 계정 전용으로 유지 ·
지금 있는 데이터는 관리자 계정의 것으로 옮긴다.

지금 나비스는 한 사람용이다. 로그인은 웹에 들어오는 문일 뿐이고 기억 · 대화 · 설정에는 주인이
없다(001 스펙 FR-046, 헌장 원칙 II). 이 기능은 로그인한 **회원마다** 자기 기억 · 대화 · 설정을
갖게 한다. 헌장 원칙 II 는 "다중 사용자로 가려면 이 항목을 먼저 개정한다"고 적고 있다 — 이 스펙이
그 개정의 근거다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 내 기억은 나만 본다 (Priority: P1)

두 사람이 각자 계정으로 나비스에 로그인해 대화한다. 각자 말한 것은 각자의 기억으로 쌓이고,
"전에 내가 뭐라고 했지?"라고 물으면 **자기** 기억에서만 찾아 답한다. 상대의 기억 · 대화방 ·
할 일 · 프로젝트 이름은 어디에도 보이지 않는다.

**Why this priority**: 이 기능의 존재 이유다. 분리가 한 군데라도 새면 다른 기능이 다 돼도 쓸 수
없다 — 기억에는 개인적인 결정 · 감정 · 사람에 관한 것이 담긴다.

**Independent Test**: 회원 A 와 B 로 각각 로그인해 서로 다른 사실을 말하게 한 뒤, A 로 로그인해
대화 · 기억 화면(목록 · 검색 · 비슷한 기억 · 할 일 · 프로젝트 목록 · 내보내기) 어디에서도 B 의
것이 나오지 않는지 확인한다. B 로도 반대로 확인한다.

**Acceptance Scenarios**:

1. **Given** A 가 "점심은 국밥"을, B 가 "점심은 파스타"를 말해 각자 저장됐다, **When** A 가
   "내 점심 메뉴 뭐였지?"라고 묻는다, **Then** 국밥만 근거로 답하고 파스타는 언급하지 않는다.
2. **Given** B 의 대화방이 여러 개 있다, **When** A 가 로그인한다, **Then** A 의 방 목록에
   B 의 방이 하나도 없다.
3. **Given** B 의 기억이 있다, **When** A 가 기억 화면에서 목록 · 검색 · 할 일 · 프로젝트
   목록을 본다, **Then** B 의 기억 · 할 일 · 프로젝트 이름이 나오지 않는다.
4. **Given** A 가 자기 기억 하나를 펼친다, **When** 비슷한 기억이 보인다, **Then** 그 목록에
   B 의 기억이 없다 — 내용이 거의 같아도.
5. **Given** A 가 기억을 내보낸다, **When** 파일을 연다, **Then** A 의 기억만 들어 있다.
6. **Given** A 가 B 의 대화방이나 기억의 식별자를 어떻게든 알아냈다, **When** 그것을 직접
   열거나 · 고치거나 · 지우려 한다, **Then** "없음"으로 거절되고 B 의 데이터는 바뀌지 않는다.

### User Story 2 - 지금 쓰던 기억은 그대로 내 것이다 (Priority: P1)

지금 나비스를 쓰는 사람(관리자)이 이 기능이 들어간 뒤 로그인하면, 그동안 쌓인 기억 · 대화방 ·
설정이 전부 그대로 있다. 아무것도 사라지거나 다른 사람에게 가지 않는다.

**Why this priority**: 분리를 넣다가 지금의 기억을 잃으면 기능의 의미가 없다. 1천 건이 넘는
기억이 이미 있다.

**Independent Test**: 전환 전 기억 · 대화방 · 할 일의 개수와 내용을 적어 두고, 전환 후 관리자
계정으로 로그인해 같은지 확인한다. 새로 만든 회원 계정으로 로그인하면 아무것도 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 전환 전 기억이 N 건, 대화방이 M 개 있다, **When** 전환 후 관리자로 로그인한다,
   **Then** 기억 N 건 · 대화방 M 개가 그대로 보이고 내용이 같다.
2. **Given** 전환 후 새 회원 계정을 만들었다, **When** 그 계정으로 처음 로그인한다,
   **Then** 기억 · 대화방이 하나도 없고 Claude 토큰도 "등록되지 않음"이다.
3. **Given** 관리자가 전환 전에 Claude 토큰을 등록해 뒀다, **When** 전환 후 대화한다,
   **Then** 다시 등록하지 않아도 답이 온다.

### User Story 3 - 각자 자기 Claude 토큰으로 대화한다 (Priority: P2)

회원은 설정 화면에서 **자기** Claude 구독 토큰을 등록한다. 나비스는 그 회원의 대화에 그 회원의
토큰만 쓴다. 한 사람의 구독을 다른 사람이 나눠 쓰지 않는다.

**Why this priority**: 토큰이 없으면 대화 자체가 안 되므로 새 회원에게는 필수다. 다만 분리
(US1)가 먼저 성립해야 의미가 있다.

**Independent Test**: A 만 토큰을 등록하고 B 는 등록하지 않은 상태에서 B 로 질문해 "설정에서
토큰을 등록하라"는 안내가 나오는지, A 의 대화는 그대로 되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** A 는 토큰을 등록했고 B 는 안 했다, **When** B 가 질문한다, **Then** 답 대신 토큰
   등록 안내가 나오고 B 의 질문은 B 의 방에 남는다. A 의 토큰으로 답하지 않는다.
2. **Given** A 와 B 가 각자 토큰을 등록했다, **When** 각자 설정 화면을 연다, **Then** 자기
   토큰의 끝 4자리 · 변경 시각만 보이고 상대 토큰의 정보는 보이지 않는다.
3. **Given** B 가 자기 토큰을 지운다, **When** A 가 대화한다, **Then** A 의 대화에는 영향이 없다.

### User Story 4 - 관리자가 회원을 들인다 (Priority: P2)

나비스에는 가입 화면이 없다. 관리자가 계정 관리 도구에서 회원 계정을 만들거나 초대하면, 그
사람이 로그인해 쓸 수 있다. 계정이 없는 사람은 로그인 화면 너머로 갈 수 없다.

**Why this priority**: 회원이 생기는 유일한 길이다. 공개 가입을 열지 않는 이유는 각 회원의
대화가 임베딩 같은 공용 비용을 쓰고, 기억은 사적인 데이터라 아무나 들어오게 할 이유가 없기
때문이다.

**Independent Test**: 관리자가 새 계정을 만든 뒤 그 계정으로 로그인되는지, 만들지 않은 이메일로는
로그인되지 않고 가입할 방법도 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자가 새 회원 계정을 만들었다, **When** 그 회원이 로그인한다, **Then** 빈
   나비스가 열리고 설정 화면에서 토큰을 등록하라는 안내가 보인다.
2. **Given** 계정이 없는 사람, **When** 로그인 화면을 본다, **Then** 가입 버튼이나 링크가 없다.
3. **Given** 관리자가 회원 계정을 막았다, **When** 10분 안에(세션을 폐기했으면 즉시) 그 회원이
   요청을 보낸다, **Then** 로그인 화면으로 돌아가고 데이터에 접근하지 못한다.

---

### User Story 5 - Claude Code 연결은 관리자 것이다 (Priority: P3)

관리자는 지금처럼 Claude Code 를 나비스에 연결해(외부 MCP) 기억을 저장 · 검색한다. 그 연결로
저장되는 기억은 **관리자의** 기억이고, 검색도 관리자의 기억에서만 한다. 다른 회원은 이 연결을
쓰지 않는다 — 웹 대화만 쓴다.

**Why this priority**: 지금 관리자가 매일 쓰는 흐름이라 끊기면 안 되지만, 회원별 연결은 이번
범위 밖이다.

**Independent Test**: Claude Code 에서 기억을 하나 저장한 뒤, 관리자 계정의 기억 화면에는
보이고 회원 계정에는 보이지 않는지 확인한다. Claude Code 에서 검색할 때 회원의 기억이 나오지
않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Claude Code 가 연결돼 있다, **When** 기억을 저장한다, **Then** 관리자 계정의
   기억으로 저장된다.
2. **Given** 회원 B 의 기억이 있다, **When** Claude Code 에서 검색한다, **Then** B 의 기억은
   결과에 없다.

---

### Edge Cases

- **식별자를 아는 다른 회원**: 대화방 식별자는 브라우저가 만들고, 기억 식별자는 화면에 오간다.
  남의 식별자로 열기 · 고치기 · 지우기 · 비슷한 기억 보기 · 그 방에 메시지 보내기를 시도하면
  전부 "없음"으로 거절된다. "있지만 권한이 없음"으로 구분해 알려주지 않는다 — 그러면 남의
  데이터가 존재한다는 사실이 샌다.
- **같은 방 식별자를 두 회원이 우연히 쓰면**: 다른 회원의 방에 이어 쓰지 않는다. 새 방으로
  만들어지거나 거절된다 — 남의 대화에 끼어드는 일은 없다.
- **같은 프로젝트 이름**: A 와 B 가 둘 다 "navis"라는 프로젝트를 써도 서로의 것이다. 프로젝트
  이름 바꾸기 · 합치기는 자기 기억에만 적용된다. 표기만 다른 이름 경고도 자기 프로젝트끼리만
  비교한다.
- **회원 계정이 막히거나 삭제되면**: 그 회원은 더 이상 들어오지 못한다. 그 회원의 기억 · 대화는
  남지만 아무도 볼 수 없다. 데이터를 지우는 것은 이번 범위 밖이다(Assumptions).
- **동시에 대화하는 두 회원**: 서로의 진행 중인 답이 섞이지 않는다. 한 회원의 중지 버튼이
  다른 회원의 턴을 멈추지 않는다.
- **로그인이 꺼진 로컬 개발 상태**: 로그인을 설정하지 않은 개발 환경에서는 관리자 한 사람으로
  동작한다 — 지금과 같다.
- **관리자 계정을 정하지 않은 채 배포하면**: 서버가 뜨지 않거나, 최소한 외부 MCP 를 닫는다.
  관리자를 모른 채 MCP 로 들어온 기억을 아무 계정에 넣지 않는다.
- **전환 중에 대화가 오가면**: 전환(기존 데이터를 관리자에게 옮기기) 도중 저장된 기억도 관리자
  것이 된다. 주인 없는 기억이 남지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**분리**

- **FR-101**: 모든 기억 · 대화방 · 설정은 정확히 한 회원의 것이다. 주인 없는 데이터는 없다.
- **FR-102**: 회원은 자기 데이터만 볼 수 있다. 이는 대화방 목록 · 대화 내용 · 기억 목록 · 의미
  검색 · 기간 조회 · 비슷한 기억 · 할 일 · 프로젝트 목록 · 내보내기 · 설정 상태 **전부**에
  적용된다. 예외 화면은 없다.
- **FR-103**: 회원은 자기 데이터만 고치거나 지울 수 있다. 다른 회원의 식별자로 요청하면 그
  데이터가 없는 것과 같은 응답을 받는다(존재 여부가 드러나지 않는다).
- **FR-104**: 나비스가 대화 중에 기억을 찾아보거나 저장할 때도 그 대화를 하는 회원의 기억만
  쓴다. 다른 회원의 기억이 답의 근거가 되지 않는다.
- **FR-105**: 프로젝트 이름은 회원마다 따로다. 이름 바꾸기 · 합치기 · 표기 경고는 그 회원의
  기억에만 적용된다.
- **FR-106**: 한 회원의 진행 중인 턴과 중지는 다른 회원의 턴에 영향을 주지 않는다.

**신원**

- **FR-107**: 요청이 어느 회원의 것인지는 로그인 확인을 거친 경로로만 정해진다. 브라우저가
  보낸 값(요청 본문 · 주소 · 헤더에 적힌 회원 식별자 등)을 신원으로 믿지 않는다.
- **FR-108**: 회원 계정이 막히면 **액세스 토큰이 만료되는 시간(10분) 안에** 데이터에 접근하지 못한다.
  관리자가 그 회원의 세션을 폐기하면 즉시 막힌다. (2026-10-08 조정 — 요청마다 계정 상태를 다시 묻지
  않는다, research R10)

**회원**

- **FR-109**: 공개 가입은 없다. 회원 계정은 관리자가 계정 관리 도구에서 만들거나 초대해서만
  생긴다. 로그인 화면에 가입 수단을 두지 않는다.
- **FR-110**: 관리자는 한 명이며 배포 설정으로 정해진다. 관리자도 다른 회원의 기억 · 대화를
  나비스 안에서 볼 수 없다 — 관리자는 데이터를 열람하는 권한이 아니라, 외부 MCP 의 주인이라는
  뜻이다.

**Claude 토큰**

- **FR-111**: Claude 토큰은 회원마다 따로 등록 · 교체 · 삭제한다. 대화에는 그 대화를 하는
  회원의 토큰만 쓴다. 다른 회원의 토큰으로 대신 답하지 않는다.
- **FR-112**: 001 의 토큰 규칙(원문 비노출 FR-037, 암호화 저장 FR-055, 토큰 없음 · 거부 안내
  FR-056)은 회원별로 그대로 적용된다.

**외부 MCP**

- **FR-113**: 외부 MCP(Claude Code 연결)로 저장 · 검색 · 수정되는 기억은 관리자의 것이다.
  다른 회원의 기억은 MCP 로 보이지도 바뀌지도 않는다.

**전환**

- **FR-114**: 이 기능이 들어가기 전에 있던 기억 · 대화방 · 설정(등록된 Claude 토큰 포함)은
  전부 관리자의 것이 된다. 개수와 내용이 그대로 유지된다.
- **FR-115**: 전환은 한 번에 끝나는 명시적 단계다. 전환이 끝나기 전에는 새 회원이 데이터를
  쓰지 않는다 — 주인이 섞이지 않게.

### Key Entities *(include if feature involves data)*

- **회원(Member)**: 로그인 계정 하나. 계정 관리 도구가 소유한다 — 나비스는 계정을 만들거나
  비밀번호를 다루지 않는다. 나비스가 아는 것은 "이 요청은 어느 회원의 것인가" 뿐이다.
- **관리자(Owner)**: 회원 중 한 명. 배포 설정으로 정한다. 기존 데이터의 주인이고 외부 MCP 의
  주인이다. 다른 회원의 데이터를 보는 권한은 없다.
- **기억 · 대화방 · 설정**: 001 의 것과 같다. 각각 한 회원에 속한다는 점만 달라진다.
  설정은 회원마다 Claude 토큰 하나를 갖는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: 두 회원의 데이터를 섞어 둔 상태에서, FR-102 에 적힌 모든 화면과 대화 응답을
  점검했을 때 다른 회원의 데이터가 나오는 경우가 **0건**이다.
- **SC-102**: 다른 회원의 식별자로 열기 · 고치기 · 지우기 · 메시지 보내기를 시도했을 때 성공하는
  경우가 **0건**이고, 응답만으로 그 데이터가 있는지 알 수 있는 경우도 0건이다.
- **SC-103**: 전환 전후로 관리자의 기억 · 대화방 · 할 일의 개수와 내용이 **100%** 같다.
- **SC-104**: 관리자가 새 회원 계정을 만들고, 그 회원이 로그인해 토큰을 등록하고 첫 답을
  받기까지 **5분 안에** 끝난다.
- **SC-105**: 기억 목록 · 검색 · 방 목록의 응답 시간이 이 기능 전과 비교해 체감할 만큼(두 배
  이상) 느려지지 않는다. 회원 수가 늘어도 한 회원이 보는 속도는 그 회원의 데이터 양에만 달려
  있다.

## Assumptions

- **회원 수는 작다** — 가족 · 지인 · 동료 수준(수 명~수십 명). 대규모 서비스의 요금 · 사용량
  제한 · 감사 로그는 범위 밖이다. 서버 인스턴스 하나 구성(001 의 배포 절)을 유지한다.
- **임베딩(기억 검색) 비용은 공용이다.** 회원마다 따로 키를 받지 않는다. 그래서 공개 가입을
  열지 않는다.
- **계정 관리는 지금의 인증 제공자가 한다.** 회원 만들기 · 초대 · 막기 · 비밀번호 재설정은
  그 도구의 화면에서 하고, 나비스에 관리 화면을 만들지 않는다.
- **회원 데이터 삭제**(탈퇴 시 기억 · 대화 일괄 삭제)와 **회원 간 공유**(기억을 다른 회원에게
  보여주기)는 범위 밖이다. 막힌 회원의 데이터는 남지만 아무도 보지 못한다.
- **회원별 외부 MCP 연결**은 범위 밖이다. 다른 회원이 Claude Code 를 연결하는 길은 다음 기능으로
  미룬다.
- **로그인이 꺼진 로컬 개발 환경**은 관리자 한 사람으로 동작한다 — 지금처럼 로그인 없이 개발할
  수 있다.
- **설정 암호화 키는 하나다.** 회원마다 다른 키를 두지 않는다. 회원 간 분리는 "누구의 행인가"로
  하고, 암호화는 DB 가 새는 경우를 막는다(001 FR-055).
- 헌장 원칙 II 의 "기억 · 대화 · 설정에 사용자 식별자 열을 두지 않는다"는 이 기능과 정면으로
  충돌한다. 계획 단계 전에 헌장을 개정한다(MAJOR — 원칙의 재정의).
