# Research: 전하기 (specs/004)

스펙의 미결 사항과 구현 방향을 코드에 맞춰 정한다. 형식: 결정 / 근거 / 기각한 대안.

---

## R1. 약속 행을 재사용하지 않고 `relays` 표를 따로 둔다

**결정**: 전하기는 `promises` 행이 아니라 새 표 `relays` 의 한 행이다. 실행 · 전달 부품(`deliver`, `runTurn`,
실행기 큐, 임대 선점 패턴)은 그대로 쓴다.

**근거**:
- `promises` 는 받는 회원의 행이라 받는 회원의 약속 화면(`GET /promises`)에 지시 원문이 그대로 보인다 — FR-011 ·
  US1-3("지시 원문은 어디에도 보이지 않는다") 위반이다.
- 약속 턴은 `promises.user_id` 의 토큰으로 돈다. 전하기는 보낸 관리자의 토큰으로 돌아야 한다(FR-022). 약속에
  "토큰 주인" 열을 더하면 회원이 만든 약속에도 그 열이 생겨 오용될 자리가 남는다.
- 약속에는 "조용함"이 정상인데 전하기에는 없다(FR-013). 같은 실행 경로에서 두 규칙을 분기하면 약속 쪽이 흐려진다.
- 헌장 원칙 I: 약속에 `kind` 같은 종류 구분을 두지 않는다. `promises.kind = 'relay'` 는 그것을 깬다.

**기각한 대안**: *즉시 실행 1회 약속(사용자 입력의 구현 방향)* — 위 네 이유. 구현 방향은 "실행 부품 재사용"으로
살리고 저장만 나눈다.

## R2. 실행은 tick 이 집는다 — 두 입구 모두 "넣기"만 한다

**결정**: 화면(`POST /relays`)과 대화 도구(`relay`)는 `relays` 에 `pending` 행을 넣고 끝낸다. 실행은 기존
`/internal/tick` 이 약속과 함께 선점해 같은 실행기 큐(`apps/server/src/promise-runner.ts`)에 세운다.

**근거**:
- 대화 도구는 `packages/domain` 안에서 돈다. domain 은 server 의 큐를 import 할 수 없다(원칙 II — 의존은 아래로만).
- Cloud Run 은 응답을 보낸 뒤 CPU 를 거의 주지 않는다(specs/003 R2). `POST /relays` 가 202 를 먼저 주고 뒤에서 돌리면
  멈춘다. 응답을 붙들고 돌리면 관리자 화면이 수십 초 멈추고, 대화 도구 안에서 돌리면 에이전트 턴 안에 또 턴이 생겨
  "약속 턴은 한 번에 하나"(성능 절) 상한이 깨진다.
- tick 은 1분마다다. 선점 → 받는 회원의 대화가 끝나길 기다림 → 턴 실행이면 SC-002(3분 안 95%)를 지킨다.
- 받는 회원의 진행 중 대화를 기다리는 규칙(`turns.waitUntilIdle`)과 서버가 죽었을 때의 임대 회수를 공짜로 얻는다(FR-016).

**기각한 대안**: *POST 가 실행까지 붙듦* — 위 이유. *domain 에 실행 콜백 주입* — 소비자 하나를 위한 추상이다(원칙 I).

## R3. 토큰: `runTurn` 에 "토큰 주인"을 따로 받는다

**결정**: `TurnInput` 에 `tokenUserId?: string` 를 더한다. 없으면 지금처럼 `userId` 의 토큰. 전하기 턴만
`userId = 받는 회원`, `tokenUserId = 보낸 관리자` 로 부른다.

**근거**: 기억 도구 · 대화 기록 · 전달은 받는 회원의 것이어야 하고(FR-010), 토큰만 관리자의 것이어야 한다(FR-022).
두 값을 한 필드로 묶을 수 없다. 기존 주석 "다른 회원의 토큰으로 대신 답하지 않는다(specs/002 FR-111)"는 전하기에만
예외로 고쳐 적는다.

- **보내기 전 검사(FR-023)**: `relay.create` 가 `claudeToken.resolve(senderId)` 로 등록 여부를 먼저 본다. 없으면
  `ClaudeTokenMissingError` 를 던지고 행을 넣지 않는다. 실행 때 만료 · 거절은 실패 이유로 남는다.
- **범위(FR-024)**: 받는 회원의 답장 턴은 평소 대화 경로라 `tokenUserId` 가 없다 — 자동으로 받는 회원의 토큰이다.

## R4. 회원 목록: `auth.users` 를 읽고, 없으면 나비스 표에서 모은다

**결정**: domain `member.list()` 가 같은 Postgres 의 `auth.users` 에서 `id, email` 을 읽는다(삭제 · 차단된 회원 제외).
`auth` 스키마가 없으면(로컬 docker Postgres — `42P01`) `conversations.user_id` 의 서로 다른 값을 이메일 없이 돌려준다.

**근거**:
- 운영 DB 는 Supabase 이고 server 의 `DATABASE_URL` 역할은 `auth.users` 를 읽을 수 있다(인증 제공자와 같은 DB — 헌장 스택 절).
  새 비밀값(service_role 키)을 들이지 않는다(헌장 배포 절의 비밀값 목록 유지).
- 회원 이름 · 별명 표를 새로 만드는 것은 범위 밖이다(스펙 Assumptions).
- 쓰기는 하지 않는다. drizzle 스키마에 `auth.users` 를 넣지 않고 raw SQL 한 줄로 읽는다 — 마이그레이션이 남의 스키마를
  건드리지 않게.

**확인할 것**: 운영에서 server 역할의 `auth.users` SELECT 권한(quickstart S0). 없으면 R4-b 로 바꾼다.

**기각한 대안**: *R4-b BFF 가 매 요청 이메일을 헤더로 넘기고 server 가 `members` 표에 적어 둠* — 신원 계약(specs/002)을 넓힌다.
권한이 없을 때의 대안으로만 남긴다. *Supabase Admin API* — service_role 키라는 강한 비밀값이 web 또는 server 에 생긴다.

## R5. 받는 사람 고르기: 도구는 uuid 를 받지 않는다

**결정**: 대화 도구 `relay` 의 입력은 `{ to: string; instruction: string }` 이다. `to` 는 이메일 · 이메일 앞부분 · 사람이 부른
이름이고, domain 이 `member.list()` 안에서만 맞춰 본다. 정확히 하나면 넣고, 0 · 여럿이면 넣지 않고 후보 목록(이메일)을 돌려준다.
모델은 그것을 보고 관리자에게 되묻는다(FR-006 · FR-007).

**근거**: 헌장 원칙 II "모델이 보는 도구 입력 스키마에 회원 id 를 넣지 않는다". 목록 밖의 회원은 지어낼 수 없다.

맞춰 보는 규칙(순수 함수 `matchMember`): 이메일 완전 일치 → 이메일 로컬 부분 일치 → 로컬 부분이 `to` 를 포함(대소문자 무시).
앞 단계에서 하나로 정해지면 멈춘다. 이메일 없는 회원(로컬)은 uuid 앞 8자를 표시로 쓴다.

## R6. 대화 도구는 관리자 턴에만 연다

**결정**: `TurnInput` 에 `canRelay?: boolean`. server 의 chat 라우트가 `isOwner(userId)` 일 때만 참으로 넘긴다. 참이면 새
in-process MCP 서버 `relay`(도구 하나: `relay`)를 열고, 시스템 프롬프트에 짧은 절을 붙인다.

**근거**:
- domain 은 관리자가 누구인지 모른다(`NAVIS_OWNER_ID` 는 server env). 판정은 지금처럼 server 한 곳(`isOwner`)에서 한다.
- 관리자가 아닌 턴에는 도구가 아예 없다 — 모델이 거절 문구를 지어낼 필요도, 회원 목록을 볼 길도 없다(FR-002, US2-3).
  나비스는 "그런 기능이 없다"고 답하게 된다.
- 약속 턴 · 전하기 턴에는 열지 않는다. 전하기가 전하기를 낳지 않게.
- 외부 MCP(`/mcp`)에는 열지 않는다(스펙 Assumptions, 헌장 "기억 외 도구는 열지 않는다").

## R7. 전하기 턴: 전용 실행 도구 `relay_run.deliver`, 조용함 없음

**결정**: 전하기 턴은 `runTurn({ userId: 받는 회원, tokenUserId: 관리자, relayRun: { relayId, state } })`.
- 열리는 MCP: `memory`(받는 회원) + `relay_run`(도구 `deliver` 하나 — `{ text }`). 약속 관리 도구 · `relay` 도구는 없다.
- 시스템 프롬프트 절 `RELAY_RUN_PROMPT`: 다른 사람이 이 회원에게 전해 달라고 맡긴 지시다 · 반드시 `deliver` 를 한 번 부른다 ·
  지시 원문을 옮겨 적지 말고 이 회원에게 맞게 쓴다 · **지시가 출처를 밝히라고 할 때만** "관리자님이 전해 달래요" 식으로
  밝히고, 그렇지 않으면 누가 맡겼는지 말하지 않는다 · 해로운 지시(사칭 · 비밀번호 요구 · 괴롭힘)는 전하지 않는다.
- 프롬프트(사용자 메시지)는 `[전하기]\n지시: …` 와 받는 회원 "나비스" 방의 최근 기록 20개(약속 턴과 같음).
- 결과: `deliver` 가 불렸으면 `delivered`, 안 불렸으면 `failed`("나비스가 전하지 않았어요" — FR-013), 예외면 `failed`(오류 문구).
  자동 재시도는 없다(Edge Case).

**근거**: `promise_run.notify` 를 재사용하면 origin · 조용함 규칙 · memo/finish 가 따라온다. 도구 하나짜리 서버가 더 작다.
헌장의 "in-process MCP 서버는 셋뿐"은 다섯(`relay`, `relay_run` 추가)으로 개정한다(FR-020 과 함께).

## R8. 출처 기록은 저장만 하고 와이어로 내보내지 않는다

**결정**: 도착 메시지의 `messages.meta` 에 `{ relayId }` 를 남긴다. `@navis/validation` 의 `messageOriginSchema` 는 바꾸지 않고,
domain 의 행 → `Message` 매핑이 `relayId` 를 싣지 않는다. 브라우저(개발자 도구 포함)에서 보이지 않는다(FR-011 · FR-018).
`deliver` 는 origin 대신 "메타 조각"을 받도록 넓힌다.

**근거**: 받는 회원 화면의 응답 JSON 에 `kind: "relay"` 가 실리면 화면 표시가 없어도 출처가 드러난다. 내부 추적에는 DB 행으로 충분하다.

푸시 알림 제목 · 본문은 약속과 같다(`deliver` 재사용) — 최근 커밋 ffdd7bd 의 "답의 첫 마디를 제목으로" 규칙을 그대로 받는다.

## R9. 관리자에게 돌아가는 것 — 상태뿐

**결정**: 관리자 화면 · `relay` 도구 응답은 `{ id, to(이메일), instruction, createdAt, status, error, deliveredAt }` 만 준다.
`messageId` 를 와이어로 주지 않는다 — 관리자가 그 id 로 무엇을 할 수는 없지만, 지은 문장에 닿는 손잡이를 만들지 않는다(FR-019).

- 실패 이유는 사람이 읽는 문구다. 받는 회원의 기억 내용이 섞일 수 있는 모델 출력은 이유로 쓰지 않는다 — 실패 이유는
  예외 메시지 · 고정 문구만.
- 기록 보존: 보낸 관리자마다 최근 50개. 넣을 때 그 밖의 오래된 행을 지운다(약속 실행 기록과 같은 방식).

## R10. 관리자 화면: 별도 페이지 `/relay`

**결정**: 위쪽 바 ⋯ 메뉴에 관리자에게만 "말 걸기" 항목. 누르면 `/relay` 페이지: 회원 선택(Select) + 지시 입력 + 보내기, 아래에
최근 기록 목록(대기 중이면 몇 초마다 다시 읽음). 관리자가 아니면 BFF · server 가 403 이고, 화면은 "관리자만 쓸 수 있어요"만 그린다.

**근거**: 기존 화면 단위(`/memories`, `/settings`)와 같다. 대화 화면 안의 다이얼로그로 두면 기록 목록이 들어갈 자리가 없다.
`useIsAdmin` 은 이미 있다.

**폴링**: `pending · running` 행이 있을 때만 5초 간격으로 목록을 다시 읽는다. 없으면 멈춘다. 새 실시간 통로를 만들지 않는다.
