# 계약 — 기억 MCP (프로세스 내)

나비스가 대화 중 기억을 다루는 유일한 통로. **프로세스 안에** 등록한다 —
HTTP MCP 로 자기 자신에게 왕복하지 않는다(헌장 성능 절, R3).

## 등록

```
createSdkMcpServer({ name: 'memory', tools: [ tool(...), ... ] })
  → Options.mcpServers = { memory: <config> }
  → Options.tools = []            // 내장 도구 전면 차단. MCP 도구는 이 배열과 무관하다
  → Options.allowedTools = ['mcp__memory__save', ...]   // 승인 프롬프트 상대가 없다
```

`Options.tools` 는 **내장 도구**의 집합이며 `[]` 는 "모든 내장 도구 비활성"이다. MCP 도구는
`mcpServers` 로 따로 들어오므로 `Read`/`Write`/`Edit`/`Bash` 는 계속 존재하지 않는다(R3).

도구 이름은 `mcp__memory__<도구명>` 으로 노출된다.

## 도구

| 도구 | 입력 | 반환 | 요구 |
| --- | --- | --- | --- |
| `save` | `SaveInput` | 저장된 기억 | FR-009~014. **중복 판정을 하지 않는다** |
| `recall` | `RecallInput` | 유사 기억 + 점수 | FR-016~019 |
| `recent` | `RecentInput` | 최근 기억 | 기간·분류로 좁힌 조회 |
| `todos` | `TodosInput` | 할 일 기억 | FR-026 |
| `update` | `UpdateInput` | 수정된 기억 | FR-023, FR-024, FR-027 |
| `remove` | `RemoveInput` | `{ ok }` | FR-025 |

`graphify` 는 **등록하지 않는다**(Q2 — 범위 밖).

입력 스키마는 `@navis/validation` 의 것을 그대로 쓴다. MCP 도구 입력과 HTTP 요청 본문이 같은
모양이라 한 곳에서 정의한다는 것이 그 파일 주석의 설계다. 모델을 향한 설명문(`description`)만
이 등록부에 둔다 — 스키마에는 형태만 둔다.

## 호출 시점 — 모델이 정한다

`recall` 은 **매 턴 자동으로 부르지 않는다**(FR-052, Q5). 시스템 프롬프트가 판단 기준을 준다:

- 사용자가 과거를 물으면 **반드시** `recall` 을 부른다(FR-053).
- 인사 · 감사처럼 기억이 필요 없는 말에는 부르지 않는다 — 첫 토큰 지연이 예산이다(SC-001, SC-017).
- 기억할 가치가 있는 사실을 들으면 `save` 를 부른다. 잡담은 저장하지 않는다(US1 시나리오 2).
- `recall` 결과가 비면 **없다고 말한다**. 지어내지 않는다(FR-020).

턴이 끝난 뒤 저장 여부를 다시 판단하는 과정(사후 큐레이터)을 **넣지 않는다** — 매 턴 지연에
직접 더해진다(헌장 성능 절).

## 오류

도구 핸들러는 **타입 있는 오류**를 던진다. 한국어 메시지 문자열로 분기하지 않는다(FR-041).

| 상황 | 결과 |
| --- | --- |
| 없는 id 로 `update` · `remove` | "찾을 수 없음" 오류 → 라우트가 404 로 번역 |
| 임베딩 서비스가 200 + 빈 `data` | 타입 있는 오류. `json.data[0].embedding` 을 무가드로 읽지 않는다(FR-042, R5) |
| 임베딩 서비스 오류 · 타임아웃 | 타입 있는 오류 → 502 |

도구 안에서 오류를 삼키면 모델이 "저장했다"고 답하는데 실제로는 저장되지 않는 최악의 실패가
된다. 오류는 `CallToolResult` 로 모델에게 전달되어 답에 반영되어야 한다.
