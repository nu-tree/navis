## Clarifications

### Session 2026-09-10

- Q: 대화방을 삭제하면 그 방에서 저장된 기억은 어떻게 되고, 기억이 어느 대화에서 나왔는지를
  기록하는가? → A: 기억은 대화방과 **완전히 독립**이다. 방 삭제는 기억에 영향을 주지 않고,
  기억은 출처를 기록하지 않는다.
- Q: 같은 내용을 다시 말했을 때 "이미 있는 기억"으로 판정하는 기준을 무엇으로 삼는가?
  → A: **중복 판정을 하지 않는다.** 나비스는 항상 저장하고, 겹치는 기억의 정리는 기억 화면에서
  사용자가 한다.
- Q: 답변이 생성되는 중에 서버가 죽거나 재시작되면, 그 턴의 사용자 메시지와 부분 답변은 어떻게
  되는가? → A: **사용자 메시지는 보내는 시점에 기록하고, 답변은 완료 시 기록한다.** 중단되면
  질문은 남고 부분 답변은 남지 않는다.
- Q: 기억이 담긴 데이터베이스가 날아가면 사용자는 무엇을 되돌릴 수 있어야 하는가?
  → A: **제공자의 자동 백업 + 사용자가 기억 전체를 파일로 내보내기.** 내보낸 파일을 되가져오는
  복원 기능은 범위 밖이다.
- Q: 나비스는 모든 턴마다 관련 기억을 자동으로 찾아보는가, 아니면 필요하다고 판단할 때만 찾는가?
  → A: **나비스가 필요하다고 판단할 때만 찾는다.** 매 턴 자동 검색하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 대화하면 기억이 쌓인다 (Priority: P1)

사용자가 나비스와 평소처럼 대화한다. 결정한 것, 알게 된 것, 떠오른 생각, 해야 할 일을
말하면 나비스가 그것을 그 대화 안에서 알아서 기억으로 남기고, 남겼다는 사실을 알려준다.
사용자는 "이거 저장해"라고 따로 지시하지 않는다.

**Why this priority**: 저장이 없으면 제2의 뇌가 아니다. 이것이 제품의 존재 이유이고,
다른 모든 이야기의 전제다.

**Independent Test**: 기억이 비어 있는 상태에서 "나 이번 분기엔 나비스에 집중하기로 했어"
라고 한 턴 보낸 뒤, 기억 목록에 그 내용이 `decision` 분류로 생겼는지 확인한다. 이것만
구현해도 "말하면 남는 노트"로서 가치가 있다.

**Acceptance Scenarios**:

1. **Given** 기억이 없는 상태, **When** 기억할 가치가 있는 사실을 말한다,
   **Then** 그 턴이 끝난 시점에 해당 내용이 기억으로 저장되어 있고 화면에 저장 표시가 보인다.
2. **Given** 잡담("고마워", "ㅇㅋ")을 보낸다, **When** 턴이 끝난다,
   **Then** 기억이 새로 생기지 않고 저장 표시도 나타나지 않는다.
3. **Given** 이미 "나비스에 집중하기로 했다"는 기억이 있다, **When** 같은 취지를 다시 말한다,
   **Then** 기억이 한 건 더 저장된다. 저장이 막히거나 사용자에게 확인을 요구하지 않는다 —
   대화 흐름을 끊지 않는 것이 중복 없음보다 우선이다.
4. **Given** 프로젝트 맥락이 있는 대화, **When** 그 맥락에서 결정을 말한다,
   **Then** 저장된 기억에 프로젝트 스코프가 붙는다.

### User Story 2 - 과거를 물으면 기억으로 답한다 (Priority: P1)

사용자가 "내가 저번에 왜 그렇게 결정했지?", "이번 주에 배운 것 정리해줘"처럼 묻는다.
나비스는 관련된 기억을 찾아 답에 반영한다. 사용자가 저장할 때 쓴 단어를 그대로 기억하고
있지 않아도 찾아야 한다.

**Why this priority**: 저장과 짝을 이루는 반쪽이다. 불러오기가 없으면 기억은 쓰이지 않는
로그일 뿐이다. 저장과 독립적으로 검증 가능하므로 별도 이야기로 둔다.

**Independent Test**: 기억 몇 건을 미리 넣어두고(사용자 이야기 1 없이 직접 주입 가능),
저장 당시와 다른 표현으로 질문했을 때 그 내용이 답에 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** "Railway 는 쓰지 않기로 했다"는 기억이 있다, **When** "배포 어디로 하기로 했었지?"
   라고 묻는다, **Then** 답에 그 결정이 반영된다.
2. **Given** 서로 다른 프로젝트의 기억이 섞여 있다, **When** 특정 프로젝트 맥락에서 묻는다,
   **Then** 그 프로젝트의 기억과 프로젝트가 없는 개인 기억만 근거로 쓰인다.
3. **Given** 오래된 기억과 최근 기억이 비슷한 내용이다, **When** 그 주제를 묻는다,
   **Then** 최근 기억이 우선해 반영된다.
4. **Given** 관련 기억이 하나도 없다, **When** 과거를 묻는다,
   **Then** 나비스는 기억이 없다고 말한다. 없는 내용을 지어내지 않는다.

### User Story 3 - 대화가 이어진다 (Priority: P2)

사용자가 어제 하던 대화방을 다시 열어 "그거 계속하자"라고 한다. 나비스는 그 방에서 무슨
이야기를 하고 있었는지 알고 이어서 답한다. 방을 여러 개 두어 주제를 분리한다.

**Why this priority**: P1 둘이 동작하면 제품은 이미 쓸 수 있다. 다만 새로고침이나 서버
재시작마다 맥락이 사라지면 실사용이 안 된다. 기능 추가가 아니라 신뢰성 확보다.

**Independent Test**: 두 턴 대화한 뒤 서버를 재시작하고 같은 방을 열어, 이전 메시지가 보이고
"방금 무슨 얘기했지?"에 답하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 메시지가 있는 방, **When** 브라우저를 새로고침한다,
   **Then** 이전 메시지가 그대로 보인다.
2. **Given** 메시지가 있는 방, **When** 서버를 재시작하고 그 방에서 다시 말을 건다,
   **Then** 나비스가 이전 맥락을 이어서 답한다.
3. **Given** 방 A 에서 "내 고양이 이름은 나비"라고 말했다, **When** 방 B 에서 고양이 이름을 묻는다,
   **Then** 방 B 의 답에 방 A 의 대화 맥락이 새지 않는다. (기억으로 저장된 내용은 예외 —
   기억은 방을 넘어 공유된다)
4. **Given** 방이 여러 개 있다, **When** 사이드바를 본다,
   **Then** 최근 활동순으로 정렬된 방 목록이 보이고, 각 방을 지울 수 있다.
5. **Given** 답변이 생성되는 중, **When** 서버가 재시작된다, **Then** 방을 다시 열면 사용자
   질문은 그대로 있고 답변만 없다. 질문을 다시 타이핑하지 않아도 된다.

---

### User Story 4 - 내 기억을 직접 관리한다 (Priority: P2)

사용자가 기억 화면을 열어 나비스가 자기에 대해 무엇을 알고 있는지 훑어본다. 틀린 것은
고치고, 남기고 싶지 않은 것은 지운다. 할 일은 따로 모아 보고 끝낸 것을 체크한다.

**Why this priority**: 자동 저장을 신뢰하려면 들여다보고 고칠 수 있어야 한다. 틀린 기억을
고칠 방법이 없으면 사용자는 자동 저장을 끄고 싶어진다.

**Independent Test**: 기억을 몇 건 넣고 화면에서 목록·검색·수정·삭제·할 일 완료를 각각
수행한 뒤, 수정한 내용이 이후 대화의 답에 반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기억이 여러 건 있다, **When** 기억 화면을 연다,
   **Then** 최신순 목록이 보이고 분류·프로젝트·기간으로 좁힐 수 있다.
2. **Given** 기억 목록, **When** 검색어를 입력한다, **Then** 의미가 가까운 기억이 나온다.
3. **Given** 내용이 틀린 기억, **When** 내용을 고쳐 저장한다,
   **Then** 목록에 반영되고 이후 검색에서도 고친 내용으로 찾힌다.
4. **Given** 할 일 분류 기억들, **When** 할 일 목록을 본다,
   **Then** 완료되지 않은 것만 보이고, 완료를 선택하면 완료된 것도 함께 보인다.
5. **Given** 기억 하나, **When** 삭제한다, **Then** 목록과 이후 답변 근거에서 사라진다.

---

### User Story 5 - 나비스의 성격을 정한다 (Priority: P3)

사용자가 설정 화면에서 나비스가 어떤 태도로 답할지 적는다. 저장하면 다음 대화부터 그
태도로 답한다.

**Why this priority**: 없어도 제품은 완전하다. 기본 성격이 마음에 안 들 때 손댈 수 있으면
좋은 정도다.

**Independent Test**: 성격을 "무조건 한 문장으로만 답한다"로 바꾸고 아무 질문을 보내
답 길이가 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 성격을 설정하지 않은 상태, **When** 설정 화면을 연다,
   **Then** 현재 적용 중인 기본 성격이 보인다.
2. **Given** 성격을 수정해 저장했다, **When** 새 턴을 보낸다, **Then** 그 태도가 반영된다.
3. **Given** 성격을 빈 값으로 저장했다, **When** 새 턴을 보낸다, **Then** 기본 성격으로 돌아간다.

---

### User Story 6 - 혼자 쓰는 나비스를 잠근다 (Priority: P2)

사용자가 나비스 주소를 열면 로그인 화면이 먼저 뜬다. 로그인하면 대화로 들어가고, 다음에 다시
열 때는 로그인 상태가 남아 바로 들어간다. 남의 손에 주소가 넘어가도 기억은 열리지 않는다.

**Why this priority**: 로컬에서 혼자 띄워 쓰는 동안은 없어도 된다. 다만 이 주소를 인터넷에
두는 순간 필수다 — 잠금이 없으면 주소를 아는 누구나 사용자의 기억 전부를 읽는다. 기능 가치가
아니라 노출 조건이므로 P1 뒤에 둔다.

**Independent Test**: 로그아웃 상태에서 대화 · 기억 · 설정 주소를 직접 입력해 전부 막히는지,
로그인 후 브라우저를 닫고 다시 열어 로그인 상태가 남는지 확인한다. 기억이나 대화 기능 없이도
검증된다.

**Acceptance Scenarios**:

1. **Given** 로그아웃 상태, **When** 기억 화면 주소를 직접 입력한다,
   **Then** 기억 내용이 보이지 않고 로그인이 요구된다.
2. **Given** 로그인한 상태, **When** 브라우저를 닫고 다시 연다, **Then** 다시 로그인하지 않고
   바로 들어간다.
3. **Given** 로그인한 상태, **When** 로그아웃한다, **Then** 모든 화면이 즉시 잠긴다.
4. **Given** 잘못된 자격, **When** 로그인을 시도한다, **Then** 로그인되지 않고 실패 사유가
   계정 존재 여부를 알려주지 않는다.

### Edge Cases

- **중지**: 사용자가 답변 중간에 중지하면 어떻게 되는가? 그 시점까지의 부분 답변은 화면에
  남고, 나비스는 실제로 생성을 멈춘다. 연결만 끊고 서버가 계속 생성하면 시간과 비용이
  계속 든다.
- **중지 뒤 다음 턴**: 중지 직후 도착한 늦은 조각이 다음 턴의 답변에 섞이면 안 된다.
- **턴 중복**: 답변이 진행 중일 때 사용자가 또 보내면? 새 턴을 만들지 않는다.
- **한글 입력 중 Enter**: 조합 중인 Enter 는 확정 키다. 이때 전송하면 마지막 글자가 잘리거나
  같은 문장이 두 번 간다.
- **의미 검색 실패**: 기억을 의미로 다루는 외부 서비스가 빈 응답이나 오류를 주면? 저장·검색이
  조용히 깨지지 않고 사용자에게 알려져야 한다.
- **없는 대상**: 이미 지운 기억이나 방을 다시 조작하면? "찾을 수 없음"으로 구분되어 다뤄지고,
  다른 실패와 섞이지 않는다.
- **찾지 않고 지나간 턴**: 나비스가 기억이 필요한 질문인데도 찾지 않고 답할 수 있다. 사용자가
  다시 물으면 그때는 찾아야 하고, 사용자가 명시적으로 요청하면 반드시 찾아야 한다(FR-053).
- **중복 누적**: 같은 사실을 여러 번 말하면 기억이 여러 건 쌓인다. 이때 불러오기 상위 결과가
  그 사실 하나로만 채워져 다른 관련 기억을 밀어낼 수 있다(SC-004 와 충돌하는 방향).
- **뒤집힌 결정**: "A 를 쓰기로 했다" 뒤에 "A 를 쓰지 않기로 했다"가 저장되면 두 건이 공존한다.
  불러오기는 더 최근 것을 우선해야 하고(FR-017), 사용자는 옛 결정을 지울 수 있어야 한다.
- **이미지만 전송**: 텍스트 없이 이미지만 보낼 수 있어야 한다.
- **방 삭제**: 방을 지우면 그 방의 메시지는 사라지지만, 그 대화 중 저장된 기억은 그대로 남는다.
  대화를 정리하는 행동이 기억을 잃게 만들면 안 된다.
- **턴 도중 서버 중단**: 답변 생성 중 서버가 죽으면 그 턴의 답변은 사라진다. 사용자 질문은
  이미 기록되어 있어야 하고, 화면은 "답변 없이 끝난 질문"을 이상하지 않게 보여줘야 한다.
- **답 없는 질문의 연속**: 중단된 질문이 방에 남은 상태에서 사용자가 다시 보내면, 같은 질문이
  두 번 보이게 된다. 사용자가 그중 하나를 지울 수 있어야 한다.
- **긴 대화**: 방의 메시지가 수백 개로 늘어나도 방 목록 조회가 느려지지 않아야 한다.
- **아주 긴 턴**: 한 턴이 분 단위로 길어질 수 있다. 그동안 사용자는 무엇이 진행 중인지 알아야
  하고, 연결이 중간에 끊기면 안 된다.
- **첫 실행**: 기억이 0건, 방이 0개인 상태에서도 화면이 비어 보이지 않고 무엇을 하면 되는지
  알 수 있어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

**대화**

- **FR-001**: 사용자는 텍스트를 입력해 나비스에게 보낼 수 있다.
- **FR-002**: 답변은 생성되는 동안 점진적으로 표시된다. 사용자는 완료를 기다리지 않고 읽기
  시작할 수 있다.
- **FR-003**: 첫 글자가 나오기 전에는 진행 중임을 알리는 표시가 보인다. 나비스가 도구를 쓰는
  중이면 어떤 작업 중인지 함께 보여준다.
- **FR-004**: 사용자는 진행 중인 답변을 중지할 수 있다. 중지하면 나비스는 실제로 생성을
  멈추고, 그 시점까지의 부분 답변은 화면에 남는다. 이 부분 답변은 기록되지 않으므로 방을
  다시 열면 사라진다 — 남는 것은 사용자의 질문뿐이다(FR-048).
- **FR-005**: 사용자가 보낸 글은 서식으로 해석하지 않고 원문 그대로 표시한다(줄바꿈 보존).
  나비스의 답변은 제목·목록·코드·표가 읽히는 형태로 표시한다.
- **FR-006**: 사용자는 한 번에 최대 8장의 이미지를 첨부할 수 있고, 텍스트 없이 이미지만으로도
  보낼 수 있다.
- **FR-007**: 사용자는 답변에 쓸 모델을 정해진 목록에서 고를 수 있다. 고르지 않으면 기본
  모델을 쓴다. 화면의 선택 목록과 서버가 허용하는 목록은 항상 같다.
- **FR-008**: 답변이 진행 중인 동안 사용자는 새 턴을 시작할 수 없다.

**기억 저장**

- **FR-009**: 나비스는 대화 중 기억할 가치가 있다고 판단한 내용을 **그 턴 안에서** 저장한다.
  턴이 끝난 뒤 저장 여부를 판단하는 추가 과정을 돌리지 않는다.
- **FR-010**: 저장이 일어난 턴은 사용자에게 저장되었음을 표시한다.
- **FR-011**: 나비스는 저장 시 기존 기억과의 중복을 판정하지 않는다. 기억할 가치가 있다고
  판단하면 이미 비슷한 기억이 있어도 항상 새로 저장한다. 겹치는 기억의 정리는 사용자가 기억
  화면에서 한다(FR-047).
- **FR-012**: 기억은 분류(결정 · 배움 · 아이디어 · 감정 · 사람 · 할 일)를 가질 수 있다.
- **FR-013**: 기억은 프로젝트 스코프를 가질 수 있다. 스코프가 없는 기억은 개인 · 전역 기억이다.
  분류와 프로젝트는 서로 독립된 축이다.
- **FR-014**: 기억에는 자유 태그를 붙일 수 있다.
- **FR-015**: 기억은 대화방과 독립이다. 방을 삭제해도 그 대화 중 저장된 기억은 남는다.
  기억은 어느 대화에서 나왔는지를 기록하지 않는다.

**기억 불러오기**

- **FR-016**: 나비스는 사용자의 질문과 **의미가 가까운** 기억을 찾는다. 저장 당시와 같은 단어를
  쓰지 않아도 찾아야 한다.
- **FR-017**: 비슷한 정도가 대등하면 더 최근의 기억을 우선한다.
- **FR-018**: 프로젝트 맥락이 주어지면 그 프로젝트의 기억과 프로젝트 없는 개인 기억만 후보로
  삼는다.
- **FR-019**: 한 번의 불러오기가 반환하는 기억 수에는 상한이 있다(최대 50건).
- **FR-020**: 관련 기억이 없으면 나비스는 없다고 말한다. 기억에 없는 내용을 사실처럼 말하지
  않는다.
- **FR-052**: 불러오기는 나비스가 필요하다고 판단한 턴에만 일어난다. 매 턴 자동으로 기억을
  뒤지지 않는다 — 인사 · 감사처럼 기억이 필요 없는 말에는 검색 비용이 붙지 않아야 한다.
- **FR-053**: 사용자가 기억을 찾아보라고 명시적으로 요청하면(예: "내가 전에 뭐라고 했지?")
  나비스는 반드시 찾는다. 판단에 맡기는 것은 사용자가 요청하지 않은 턴에 한한다.

**기억 관리 화면**

- **FR-021**: 사용자는 기억 목록을 최신순으로 볼 수 있고, 분류 · 프로젝트 · 기간으로 좁힐 수
  있다.
- **FR-022**: 사용자는 기억을 직접 검색할 수 있고, 결과는 대화에서의 불러오기와 같은 기준으로
  정렬된다.
- **FR-023**: 사용자는 기억의 내용 · 분류 · 프로젝트 · 태그를 수정할 수 있다.
- **FR-024**: 내용을 수정하면 이후 검색에서도 수정된 내용으로 찾힌다.
- **FR-025**: 사용자는 기억을 삭제할 수 있다. 삭제된 기억은 목록과 이후 답변 근거에서 사라진다.
- **FR-026**: 사용자는 할 일 분류 기억만 따로 볼 수 있다. 기본으로 미완료만 보이고, 선택하면
  완료된 것도 함께 보인다.
- **FR-027**: 사용자는 할 일을 완료 · 미완료로 바꿀 수 있다.
- **FR-028**: 기억을 서로 연결해 관련 기억으로 묶을 수 있다.
- **FR-047**: 사용자는 서로 겹치는 기억을 찾아낼 수 있다. 기억 목록은 의미가 가까운 항목을
  나란히 보여주고, 사용자가 그중 남길 것을 고르고 나머지를 지울 수 있게 한다. 중복 판정을
  자동으로 하지 않기로 했으므로(FR-011) 이 정리 수단이 유일한 누적 방지책이다.
- **FR-050**: 사용자는 자신의 기억 전체를 파일 하나로 내보낼 수 있다. 파일에는 각 기억의
  내용 · 분류 · 프로젝트 · 태그 · 완료 여부 · 생성 시각이 담기고, 나비스 없이도 사람이 읽을 수
  있는 형식이어야 한다.
- **FR-051**: 내보내기는 기억이 0건이어도 실패하지 않고 빈 목록이 담긴 유효한 파일을 만든다.

**대화 이력**

- **FR-029**: 대화는 방 단위로 보존된다. 새로고침과 서버 재시작 후에도 방과 그 안의 메시지가
  남는다.
- **FR-030**: 방을 다시 열면 나비스는 그 방의 이전 맥락을 이어서 답한다.
- **FR-031**: 방이 다르면 대화 맥락이 섞이지 않는다. 단, 기억으로 저장된 내용은 방을 넘어
  공유된다.
- **FR-032**: 방 목록은 최근 활동순으로 보이고, 각 방의 요약(제목 · 마지막 메시지 · 메시지 수)만
  싣는다. 목록 조회가 모든 방의 전체 메시지를 실어오지 않는다.
- **FR-033**: 사용자는 새 방을 만들고 방을 삭제할 수 있다.
- **FR-034**: 방 제목은 첫 사용자 메시지에서 자동으로 정해진다.
- **FR-035**: 모든 메시지와 방은 충돌하지 않는 식별자를 갖는다. 같은 순간에 만들어진 둘이 같은
  식별자를 갖지 않는다.
- **FR-048**: 사용자 메시지는 **보내는 시점에** 방에 기록된다. 나비스의 답변은 턴이 완료된
  시점에 기록된다. 새 방이면 첫 메시지를 보낼 때 방이 만들어진다.
- **FR-049**: 턴이 중단되거나 서버가 재시작되면 사용자 메시지는 남고 답변은 남지 않는다.
  사용자는 방을 다시 열어 자기 질문을 확인하고 다시 보낼 수 있다. 사용자가 쓴 글은
  어떤 실패에서도 유실되지 않는다.

**설정**

- **FR-036**: 사용자는 나비스의 성격(답하는 태도)을 보고 수정할 수 있다. 저장하면 이후 턴에
  반영된다.
- **FR-037**: 성격이 비어 있으면 내장 기본값이 쓰인다.

**접근과 오류**

- **FR-038**: 브라우저는 나비스 서버를 직접 부르지 않는다. 서버 접근 자격은 브라우저에 노출되지
  않는다.
- **FR-039**: 나비스는 사용자의 파일을 읽거나 쓰거나 명령을 실행할 수 없다. 쓸 수 있는 도구는
  기억 관련 도구뿐이다.
- **FR-040**: 실패한 턴은 사용자가 읽을 수 있는 메시지로 알려진다. 실패해도 방의 기존 메시지는
  남는다.
- **FR-041**: 없는 기억 · 없는 방에 대한 요청은 "찾을 수 없음"으로 구분되어 다뤄진다. 오류
  문구를 다듬는 것이 처리 결과를 바꾸지 않는다.
- **FR-042**: 의미 검색을 담당하는 외부 서비스가 빈 응답이나 오류를 주면, 저장 · 검색은 조용히
  실패하지 않고 사용자에게 알려진다.

**로그인**

- **FR-043**: 사용자는 로그인해야 나비스를 쓸 수 있다. 로그인하지 않은 상태에서는 대화 · 기억 ·
  설정 어느 화면도 내용을 보여주지 않고, 어떤 기억이나 대화도 조회되지 않는다.
- **FR-044**: 로그인 상태는 브라우저를 닫고 다시 열어도 유지된다. 사용자는 명시적으로 로그아웃할
  수 있고, 로그아웃하면 즉시 모든 화면이 잠긴다.
- **FR-045**: 잘못된 자격으로는 로그인되지 않는다. 실패 사유가 계정의 존재 여부를 알려주지
  않는다.
- **FR-046**: 로그인은 웹 접근을 막는 문이다. 기억과 대화에는 소유자 구분이 없다 — 로그인한
  사용자는 저장된 모든 기억과 대화를 본다.

### Key Entities *(include if feature involves data)*

- **기억 (Memory)**: 사용자에 대해 남긴 한 조각의 사실. 내용, 분류(선택), 프로젝트
  스코프(선택), 태그 목록, 완료 여부(할 일인 경우), 생성 시각, 그리고 의미로 찾기 위한
  표현을 갖는다. 관련 기억끼리 연결될 수 있다. **대화방을 참조하지 않는다** — 기억은 방보다
  오래 살고, 어느 대화에서 나왔는지는 남기지 않는다.
- **대화방 (Conversation)**: 하나의 주제로 이어지는 대화. 제목, 메시지 목록, 맥락을 이어가기
  위한 참조, 생성 시각, 마지막 활동 시각을 갖는다.
- **메시지 (Message)**: 방 안의 한 발언. 누가 말했는지(사용자 · 나비스), 텍스트, 시각,
  그 턴에 쓰인 도구의 라벨(선택), 첨부 이미지(선택)를 갖는다.
- **턴 (Turn)**: 질문 하나와 그에 대한 답변 하나. 중지의 단위이며 고유하게 식별된다.
- **설정 (Setting)**: 키와 값 한 쌍. 현재는 나비스의 성격 하나만 쓴다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 짧은 인사나 단순 질문에 대해, 보낸 뒤 **3초 안에** 첫 글자가 화면에 나타난다.
- **SC-002**: 중지를 누르면 **2초 안에** 실제 생성이 멈춘다. 멈춘 뒤 추가 비용이 발생하지 않는다.
- **SC-003**: 기억할 내용이 담긴 대화 턴 중 **90% 이상**에서, 사용자의 별도 지시 없이 기억이
  저장된다.
- **SC-004**: 과거에 말한 사실을 다른 표현으로 물었을 때, 해당 기억이 후보 상위 5개 안에
  포함되는 비율이 **90% 이상**이다.
- **SC-005**: 같은 사실이 3건으로 쌓인 상태에서, 사용자가 기억 화면에서 그 3건을 찾아 1건으로
  줄이는 데 **1분 안에** 끝낸다.
- **SC-006**: 서버를 재시작한 뒤에도 모든 방과 메시지가 남아 있고, 맥락 이어가기가 **100%**
  유지된다.
- **SC-007**: 기억 1,000건 기준으로 기억 목록 첫 화면이 **1초 안에** 보인다.
- **SC-008**: 사용자가 틀린 기억 하나를 찾아 고쳐 저장하는 데 **30초 안에** 끝낸다.
- **SC-009**: 방이 200개, 각 방 메시지가 500개인 상태에서 방 목록이 **1초 안에** 보인다.
  방이 10개일 때 대비 조회 시간 증가가 **2배 이내**다.
- **SC-010**: 제품 표면이 **대화 · 기억 · 설정 세 화면**을 넘지 않는다.
- **SC-011**: 브라우저가 받는 어떤 응답에도 서버 접근 자격이 담기지 않는다. 확인 방법: 브라우저
  네트워크 기록과 스크립트 번들 전체 검색에서 **0건**.
- **SC-012**: 처음 여는 사용자가 안내 없이 첫 기억을 남기는 데 성공하는 비율이 **80% 이상**이다.
- **SC-013**: 로그아웃 상태에서 대화 · 기억 · 설정의 어떤 주소를 직접 입력해도 데이터가 보이는
  경우가 **0건**이다.
- **SC-014**: 로그인한 사용자가 다음 방문 시 다시 로그인을 요구받지 않는다. 재로그인 요구 빈도는
  **7일에 1회 이하**.
- **SC-015**: 사용자가 보낸 메시지가 유실되는 경우가 **0건**이다. 턴 실패 · 중지 · 서버 재시작을
  각각 10회 시도해도 질문은 모두 방에 남아 있다.
- **SC-016**: 기억 1,000건을 내보내는 데 **10초 안에** 끝난다. 내보낸 파일만 보고 모든 기억의
  내용 · 분류 · 생성 시각을 확인할 수 있다 — 누락 필드 **0건**.
- **SC-017**: 인사 · 감사처럼 기억이 필요 없는 말 10턴에서 기억 검색이 일어나는 횟수가
  **0회**다. 같은 10턴의 첫 글자 도착 시간이 SC-001 의 3초를 넘지 않는다.
- **SC-018**: 사용자가 명시적으로 과거를 물은 턴에서 나비스가 기억을 찾는 비율이
  **100%** 다.

## Assumptions

**사용자와 환경**

- 사용자는 **한 명**이고 계정도 하나다. 웹은 로그인으로 잠그되(FR-043~046), 그것은 접근을
  막는 문일 뿐이고 데이터에 소유자 구분을 두지 않는다 — 기억 · 대화에 사용자 식별자를 붙이지
  않는다. 여러 사용자 간 권한 구분 · 공유 · 초대는 범위 밖이다.
- 나비스 서버는 사용자의 신원을 모른다. 웹이 로그인을 확인한 뒤 자기가 쥔 자격으로 서버를
  부르고, 서버는 그 자격만 검증한다. 단일 사용자라 이것으로 충분하다.
- 서버가 유일한 권위이므로 기기 간 충돌 해소(Last-Write-Wins, 툼스톤, 스냅샷 업로드)는
  범위 밖이다.
- 화면은 **웹 하나**다. 모바일 앱은 범위 밖이지만, 계약은 이후 모바일이 같은 서버를 부를 수
  있는 형태로 유지한다.
- 배포 대상은 아직 정하지 않는다. 검증은 로컬 개발 환경(웹 · 서버 각각 기동) 기준으로 한다.

**의존**

- 대화 응답은 외부 모델 서비스에 의존한다. 그 서비스가 실패하면 턴이 실패하고 사용자에게
  알려진다.
- 기억의 의미 검색은 외부 임베딩 서비스에 의존한다. 저장과 검색 모두 이 서비스가 필요하다.
- 로그인은 **이미 쓰고 있는 관리형 Postgres 제공자(Supabase)의 인증 기능**을 그대로 쓴다.
  데이터베이스가 이미 그 제공자 위에 있어(`apps/server/.env.example`, `packages/db/src/client.ts`)
  계정 저장소와 인증 API 가 함께 딸려 온다 — 새 인프라를 세우지 않고, 비밀번호를 직접 저장하거나
  해시하지 않는다. 다만 클라이언트 라이브러리는 아직 저장소에 없으므로 새로 들인다.
- 저장된 데이터의 백업은 **관리형 데이터베이스 제공자의 자동 백업**에 의존한다. 나비스가 자체
  백업 일정을 돌리지 않는다. 제공자 장애나 계정 사고에 대한 사용자 측 대비책은 기억
  내보내기(FR-050)다.
- 기억은 이전 구현(정리 직전 커밋 `b5f05b2`)에서 이관된다. `STRUCTURE.md` 의 "이관하면서
  반드시 반영할 것" 8개 항목은 이 스펙의 수용 조건에 포함된다 — 특히 의미 검색 응답의 무가드
  접근, 문자열 기반 오류 분기, 목록 조회의 과다 적재는 그대로 옮기지 않는다.

**기억 동작의 기본값**

- 저장은 **자동이 기본**이다. 사용자가 대화 중 명시적으로 저장을 지시하는 별도 조작은 만들지
  않는다. 대신 기억 화면에서 직접 추가 · 수정 · 삭제할 수 있다.
- 불러오기는 **나비스의 판단**에 맡긴다(FR-052). 매 턴 강제 검색보다 첫 토큰 지연(SC-001)을
  우선한 선택이며, 대가는 찾아야 할 턴에 찾지 않을 위험이다. 사용자의 명시적 요청은 그
  판단을 건너뛴다(FR-053).
- **중복 판정은 하지 않는다.** 저장 경로에 중복 검사를 두지 않아 대화 흐름이 끊기지 않고
  저장이 빨라진다. 대가는 기억 누적이며, 그 정리 책임은 사용자와 기억 화면에 있다(FR-047).
- 기억은 자동으로 만료되지 않는다. 삭제는 사용자의 명시적 행동으로만 일어난다.
- 첨부 이미지는 그 턴의 입력으로만 쓰고 원본을 보관하지 않는다.

**명시적 범위 밖** (헌장 원칙 I — 다시 들여오려면 헌장을 먼저 개정한다)

- 크론 · 예약 실행, 기억 다이제스트, 캘린더 연동, 동적 외부 커넥터, 푸시 알림,
  자기수정 파이프라인
- 매 턴 뒤에 도는 사후 큐레이터 (저장 판단은 턴 안에서 끝낸다)
- 나비스에게 주는 파일 · 셸 도구
- 기기 간 동기화, 대화 공유
- **대화 내보내기**와 **가져오기(복원)**. 기억 내보내기(FR-050)만 범위 안이다 — 내보낸 파일을
  되읽어 기억을 되살리는 기능은 별도로 뺀다
- 데스크톱 앱, 터미널 CLI
- **기억 그래프 시각화**. `STRUCTURE.md` 의 이관 지도에는 `graphify` 가 남아 있고
  `packages/validation/src/memory.ts` 에 입력 계약도 이미 있지만, `plan.md` 의 "부수 기능은
  전부 지운다"를 따른다. 세 화면(대화 · 기억 · 설정)을 넘지 않는다(SC-010). 쓰이지 않는 그
  입력 계약은 정리 대상이다. 기억끼리 연결하는 것(FR-028)은 범위 안이고, 그것을 **그림으로
  보여주는 화면**만 범위 밖이다.
- **외부 도구에 기억을 개방하는 통로**. `apps/server/src/app.ts` 주석이 예고하지만 부를 소비자가
  아직 없다 — 헌장 원칙 I("소비자가 실재하지 않는 라우트를 만들지 않는다")에 따라 만들지 않고,
  그 예고 주석도 정리 대상이다.
- 다중 사용자 · 계정 초대 · 데이터 소유자 분리
