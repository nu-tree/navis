# Research: 주제 대화

스펙의 확인 항목은 모두 풀렸다(예전 방 — A, 운영에 남은 방 0개). 여기서는 설계 선택을 정한다.

## R1. 주제는 기억의 프로젝트 그대로 — 방에 `project` 열 하나

- **Decision**: `conversations` 에 `project text null` 열을 더한다. null 이면 주제 없는 방("나비스" 방, 또는 예전 방).
  주제 방은 `project` 가 있는 방이다. 새 표를 만들지 않는다.
- **Rationale**: 스펙 가정 — 주제는 새 개념이 아니라 `memories.project` 다. 방이 같은 문자열을 들고 있으면 기억 범위 · 개수 ·
  이름 바꾸기가 기존 쿼리(`eq(memories.project, …)`)를 그대로 쓴다.
- **Alternatives**: `topics` 표 + 외래 키 — 프로젝트 이름의 주인이 둘이 되어 rename 때 두 곳을 맞춰야 한다. 기각.

## R2. 주제 하나에 방 하나 — 유일 인덱스 없이 "있으면 연다"

- **Decision**: DB 유일 인덱스를 두지 않는다. 방 만들기는 "그 회원 · 그 프로젝트의 방이 있으면 그것을 돌려주고, 없으면
  만든다"(`openTopicRoom`). 화면은 만드는 동안 버튼을 잠근다.
- **Rationale**: 스펙 Edge Case — 두 주제를 합치면 같은 주제 방이 둘이 될 수 있고 **둘 다 남긴다**. `(user_id, project)` 유일
  인덱스를 걸면 rename 이 그 순간 실패한다. 회원 한 명이 동시에 같은 주제 방을 두 번 만드는 경합은 화면 잠금으로 충분하다.
- **Alternatives**: 유일 인덱스 + 합칠 때 한쪽 방을 지움 — 대화 기록을 자동으로 지우게 된다(스펙 위반). 유일 인덱스 + 합칠 때
  옛 방을 옛 이름에 남김 — 기억 0개짜리 유령 방이 생긴다. 기각.

## R3. 초점은 프롬프트가 아니라 도구가 건다

- **Decision**: 기억 MCP 서버에 `focus?: string`(방의 프로젝트)을 넘긴다. focus 가 있으면 핸들러가 기본값을 채운다.
  - `recall` · `recent` · `todos`: `project` 가 비었으면 focus 로 좁힌다(그 주제 + 개인 기억 — 기존 기본 규칙).
    입력에 `everywhere: true` 가 오면 좁히지 않는다(FR-006).
  - `save`: `project` 가 비었으면 focus 로 남긴다. `personal: true` 면 주제 없이 남긴다(R4).
  - 모델이 `project` 를 직접 주면 그것이 이긴다 — "이건 회사 일이야"(FR-007).
  - 시스템 프롬프트에는 "이 방의 주제" 절을 짧게 붙인다 — 넓히기 · 개인 사실 · 약속 안내(FR-020)만.
- **Rationale**: SC-002 · SC-003 은 90% 를 요구한다. 모델이 매번 `project` 를 채우기를 기대하면 빠뜨리는 턴이 생긴다. 기본값을
  코드가 채우면 모델이 아무것도 안 해도 초점이 맞고, 모델이 하는 일은 예외(넓히기 · 다른 주제 · 개인)를 말하는 것뿐이다.
  `everywhere` 가 입력 하나에만 붙으므로 넓힘이 다음 질문으로 이어지지 않는다(FR-006) — 상태를 들고 있지 않다.
- **Alternatives**: 프롬프트만으로 "project 를 X 로 넣어라" — 확률적, 기각. 서버가 범위를 강제하고 넓히기를 막음 — 스펙의
  "격리가 아니라 초점" 위반, 기각.
- **외부 MCP**: focus 를 넘기지 않는다. `everywhere` · `personal` 은 focus 가 없으면 아무 효과가 없다 — 스키마는 하나로 둔다
  (헌장: 외부 MCP 와 대화가 같은 정의를 쓴다).

## R4. 주제 방에서 말한 개인 사실

- **Decision**: `save` 입력에 `personal?: boolean` 을 더한다. 주제 방에서 생일 · 취향 · 건강처럼 주제와 무관한 사용자 자신의
  사실은 `personal: true` 로 남기라고 도구 설명 · "이 방의 주제" 절에서 안내한다. 스펙 FR-007 에 이 예외를 적는다.
- **Rationale**: 이사 방에서 "나 다음 달 생일이야"가 '이사'로 분류되면 다른 방에서 개인 기억으로 보이지 않는다. 개인 기억은
  모든 방에서 쓰이는 것이 정의다.
- **Alternatives**: `project: ""` 로 개인 지정 — `projectSchema` 가 min(1) 이고, 빈 문자열의 뜻을 모델이 추측해야 한다. 기각.

## R5. 방 만들기 엔드포인트를 연다

- **Decision**: `POST /conversations { project }` → 그 주제 방(있으면 기존). 지금은 방 생성을 `POST /chat` 이 겸한다는 규칙이
  있지만(conversations 라우트 주석), 주제 방은 첫 메시지 전에 칩(바탕 기억)이 보여야 하고 "있으면 연다"를 해야 한다 — 소비자가
  생겼다(헌장 원칙 I).
- **Alternatives**: 첫 메시지에 project 를 실어 `POST /chat` 이 만들게 — 빈 방에서 칩이 안 보이고, 같은 주제 방을 찾는 판단이
  채팅 라우트에 섞인다. 기각.

## R6. 방 목록 · 기억 개수

- **Decision**: `GET /conversations` 의 요약에 `project: string | null` · `memoryCount: number | null` 을 더한다. 개수는 같은
  요청에서 `projects(userId)` 를 한 번 불러 맞춘다(그룹 쿼리 하나). 목록은 `isMain or project is not null` 만 — 주제 없는 예전 방은
  보이지 않는다(스펙 결정 A).
- 칩의 기억 목록은 기존 `GET /memories?project=X&exactProject=true` 를 쓴다 — 새 엔드포인트 없음.
- **Rationale**: 대화 턴 경로에는 아무것도 더하지 않는다(SC-006). 목록 조회는 화면을 열 때 · 턴이 끝난 뒤에만 돈다.

## R7. 이름 바꾸기 · 합치기가 방을 따라오게

- **Decision**: `renameProject` 의 같은 트랜잭션에서 `conversations.project = from` 인 그 회원의 방을 `to` 로, 제목도 `to` 로
  바꾼다(FR-004). 합치기로 같은 주제 방이 둘이 되면 둘 다 둔다(R2).
- **Alternatives**: 방 제목을 저장하지 않고 project 에서 매번 만든다 — 제목 열은 "나비스" 방 · 예전 방에서 계속 쓰이므로 열을 둔
  채 같이 바꾸는 편이 단순하다.

## R8. 채팅 턴에 focus 넘기기 — 추가 조회 없이

- **Decision**: `conversation.ensure()` 가 이미 방 행을 읽는다. 반환에 `project` 를 실어 chat 라우트가 `runTurn({ focus })` 로
  넘긴다. 약속 · 전하기 턴에는 focus 가 없다(언제나 "나비스" 방 · 모든 기억).
- **Rationale**: 헌장 성능 절 — 매 턴 고정 비용을 늘리지 않는다. 시스템 프롬프트는 방마다 고정이라 같은 방 안에서 프롬프트 캐시가
  깨지지 않는다.

## R9. 웹 — 열린 방을 상태로, 앱을 열면 "나비스"

- **Decision**: 열린 방 id 를 zustand 스토어(메모리, 저장하지 않음)에 둔다. 비어 있으면 "나비스" 방. 위쪽 바 왼쪽의 "나비스"
  글자를 방 메뉴 버튼(지금 방 제목 ▾)으로 바꾼다. 칩은 채팅 패널 위 한 줄, 누르면 시트에 기억 목록과 "이 방 지우기".
  알림을 눌러 열리면(`?c=`) 그 방을 연다 — `usePushBridge(open)` 에 open 을 다시 넘긴다(FR-021).
- **Rationale**: FR-018 — 앱을 열면 "나비스" 방. 사이드바를 되살리지 않는다(스펙 가정).

## R10. 헌장

- **Decision**: 기능 자체는 개정이 필요 없다 — 대화를 나누는 것이고 새 MCP 서버 · 비밀값 · 실행 경로가 없다. 다만 보안 절의
  "in-process MCP 서버는 다섯뿐"이 피드백(`feedback`, b815051)으로 이미 틀렸다. 이 기능의 첫 태스크로 v2.4.0(MINOR) 개정을 한다:
  `feedback`(회원의 대화 턴에만 — `send`)을 여섯째로 적는다.
